 1. Core Philosophy & Guiding Principles

- **Branching simulation over linear answers** — The system always produces a directed acyclic graph of decision points, possible outcomes, and failure modes. No single “correct” prediction is ever returned. Instead, users see a range of plausible futures, each backed by evidence and risk analysis.
- **Interpretation over data** — A strict architectural separation between the Data Layer (immutable facts, source chunks, entities, verified events) and the Reasoning Layer (stochastic generation, persona-driven interpretation, synthesis of alternatives). This ensures that the same data can be re‑interpreted under different assumptions without corrupting the underlying evidence.
- **Local‑first, privacy‑first** — All core computation (ingestion, embedding, reasoning, graph simulation) must be capable of running entirely on the user’s own machine, without mandatory internet connectivity or external SaaS. Cloud‑based tiers are offered for convenience, but the premium (Level 3) product never forces a user to expose their data.
- **Safety‑first by design** — Every decision node is automatically enriched with a mandatory risk layer, including severity, likelihood, and mitigation strategies. Citations must anchor every factual claim. The system actively refuses to produce output that violates these safety constraints, triggering adversarial re‑prompts until compliance is achieved.
- **Provenance everywhere** — Every piece of information flowing into a decision node is linked to a source (cache ID, URL, or internal knowledge chunk). Claims that cannot be verified are explicitly marked as `speculative` and displayed with a distinct visual treatment, preventing the user from confusing assumption with fact.
- **Persona‑driven exploration** — Users can dynamically apply different “decision lenses” (Skeptical Investor, Cautious Regulator, Aggressive Founder, Ethical Auditor, etc.) to the same scenario. Each persona biases the reasoning model with a unique prompt template, producing legally and emotionally distinct interpretations while remaining within the same factual boundaries.
- **Incremental and immutable** — When a user selects an alternative and creates a new branch, the entire upstream path (all ancestor nodes) is locked and treated as an immutable snapshot. The simulation engine only receives a compressed parent summary and the delta context; it never re‑computes or alters historical nodes, enabling both performance efficiency and full auditability.
- **Adversarial thinking as a default** — The system proactively seeks contradictory evidence, potential pitfalls, and minority viewpoints. By embedding adversarial reasoning at the core, it reduces over‑optimism and group‑think, delivering more robust decision support.
- **Continuous evolution** — The platform learns from every interaction, every new source scraped, and every piece of user feedback. The knowledge graph, source trust metrics, and user cognitive twin all evolve over time, making the system more accurate and more personalised with use.

## 2. User Interaction & Intake Flow

- **Multi‑modal, unstructured input** — The system accepts:
  - One‑line informal prompts (“Should I quit my job and start a business?”)
  - Long‑form narrative text (personal context, background)
  - File uploads: PDF reports, DOCX documents, spreadsheets, plain text files
  - Structured JSON payloads for programmatic use
  - (Future) voice input via browser or desktop integration
- **Dynamic clarification engine** — Upon receiving the raw prompt, a lightweight intent analyser determines the ambiguity level and generates 5–7 highly targeted, context‑sensitive questions. These questions:
  - Probe for missing constraints (budget, timeline, location, personal values)
  - Uncover hidden assumptions the user may be taking for granted
  - Calibrate the user’s risk appetite and decision‑making style
  - Clarify the scope and domain (career, financial, health, legal, etc.)
  - Are themselves generated by a small/fast model to minimise latency
- **Parameter collection** — Beyond free‑text answers, the intake wizard explicitly collects:
  - Simulation horizon: 3, 6, 12, or custom months
  - Risk tolerance: a simple scale (1–10) mapped to internal risk thresholds
  - Domain tags (optional) to pre‑load specialised knowledge packs
  - Preferred experience depth: Level 1 (exploration), Level 2 (enthusiast), or Level 3 (full personal command centre)
- **Conversational wizard interface** — The intake feels like a structured conversation, not a static form. The UI reveals questions one at a time with smooth transitions, progress indicators, and example answers. Users can skip questions, but the system notes missing information for later clarification.
- **Formal User Intent Object** — The output of the intake is a structured, validated `UserIntent` object that serves as the single source of truth for the subsequent simulation. This object includes all user‑provided data, extracted entities, inferred preferences, and metadata about what is known vs. what is still ambiguous.
- **Revision window** — Before the simulation launches, the user can review and modify any answer, adjust parameters, or go back to earlier questions. The system also highlights any answers that appear contradictory and suggests re‑evaluation.

## 3. Knowledge Acquisition & Ingestion

- **Advanced Deep RAG pipeline** (evolution of original v1.2):
  - **Wide‑net candidate discovery**: A search aggregator gathers metadata (title, URL, snippet, domain, date) for 15–30 candidate sources per query, using multiple search backends to ensure diversity.
  - **Intelligent filtering**: A cascade of heuristics and ML classifiers removes low‑quality domains, spam, paywalled content, and outdated material. The system maintains a dynamic domain reputation score, updated by user feedback and editorial overrides.
  - **Parallel, resource‑capped scraping**: Content is fetched concurrently using a configurable worker pool (async I/O). Memory caps and timeouts prevent runaway resource consumption, critical for desktop (Level 3) environments.
  - **Content cleaning & normalisation**: Raw HTML is sanitised, boilerplate removed, main textual content extracted using readability algorithms. The output is clean markdown or plain text, preserving the original structure (headings, paragraphs, lists).
  - **Provenance‑preserving chunking**: The cleaned text is split into segments of 400–700 characters, anchored to natural paragraph boundaries. No summarisation or paraphrasing occurs at this stage — the original wording is kept intact to support citation accuracy and later verification.
  - **Embedding & indexing**: Each chunk is embedded using a local or hosted embedding model (configurable). The resulting vector is stored alongside the chunk content, source metadata, and a unique chunk ID.
  - **KnowledgeChunk document**: Every chunk is persisted as a structured document containing: `source_url`, `source_title`, `chunk_index`, `content`, `embedding`, `created_at`, `ttl_days`, `verification_status`, and `citation_token`.
- **Hybrid retrieval strategy**:
  - **Primary**: Dense vector search (cosine similarity) with configurable minimum thresholds (strong match ≥0.85, soft match ≥0.7).
  - **Fallback**: Sparse keyword/BM25 retrieval for exact term matching, policy clauses, or low‑embedding‑coverage scenarios.
  - **Fusion**: Results from both methods are merged using Reciprocal Rank Fusion (RRF) before reranking.
- **Source verification & trust scoring**:
  - Each source (domain or individual URL) carries a dynamic trust score, initially assigned by a human‑curated seed list, then updated based on cross‑referencing consistency, user upvotes/downvotes, and expert annotations.
  - The `verification_status` of a chunk can be: `verified` (corroborated by other sources), `unverified` (single source, yet to be confirmed), or `failed` (contradicted).
  - A background re‑scraping scheduler refreshes chunks that are past their TTL, ensuring the knowledge base remains current.
- **User privacy & legal safeguards**:
  - A global “disable live scraping” toggle for privacy‑conscious users; when enabled, the system relies solely on pre‑cached or manually uploaded knowledge.
  - Full respect for `robots.txt`, rate limiting, and user‑agent identification. The system never attempts to access password‑protected or clearly private content.

## 4. Knowledge Representation & Storage (Conceptual)

- **Structured knowledge model (Knowledge Graph)** — Beyond flat, disconnected text chunks, the system maintains an interconnected graph of:
  - **Entities**: people, organisations, products, financial instruments, diseases, geographic regions, etc.
  - **Relationships**: `causes`, `supports`, `refutes`, `related_to`, `citation_of`, `depends_on`, `competes_with`
  - **Events**: temporally anchored occurrences with numeric attributes (e.g., “company X raised $50M in Q2 2026”)
  - **Quantitative facts**: extracted numeric values linked to units and context, enabling direct computation.
- **Hybrid graph‑vector store** — The storage layer combines:
  - **Graph database** (conceptual) for entity‑relationship traversal, multi‑hop reasoning, and relationship‑intensive queries.
  - **Vector index** for semantic similarity search over source chunks and entity descriptions.
  - The two are interlinked: a chunk can point to the entities it mentions; an entity can list the chunks that provide evidence about it.
- **Intelligent retrieval paths** — When a prompt mentions concept “a”, the retrieval fabric can follow edges: `a → related_to → b → supported_by → source_chunk`, thereby pulling in relevant evidence without exhaustive scanning. This graph‑guided retrieval dramatically improves recall for complex, multi‑step questions.
- **Temporal lifecycle management** — Every piece of knowledge carries a time‑to‑live (TTL) appropriate to its domain (e.g., stock prices: 1 day; medical guidelines: 6 months; company addresses: 1 year). Expired data is automatically pruned or flagged for refresh.
- **Cross‑session cache & federated knowledge** — In cloud tiers (Levels 1‑2), anonymised, aggregated knowledge chunks (with user‑specific data stripped) can be shared across sessions to accelerate warm‑start for new users. Strict tenant isolation ensures no private data leaks.

## 5. Reasoning & Decision Generation

- **Multi‑persona adversarial synthesis** — For each decision point, the system instantiates multiple independent reasoners:
  - Each reasoner is given the same evidence context but a distinct **persona prompt** (Skeptical Investor, Ethical Regulator, Aggressive Founder, Risk‑Averse Individual, etc.) and a slightly different `temperature` (0.5–0.8) to introduce controlled stochasticity.
  - Every reasoner outputs a complete, schema‑valid `DecisionNode` proposal.
  - A **Synthesis Arbiter** then ingests all proposals, performs a structured comparison (identifying areas of agreement, divergence, and unique risks), and produces a final node that represents a balanced view with explicit minority reports if necessary.
- **Strict JSON schema enforcement** — The target output schema (`DecisionNode`) includes:
  - `title`, `summary`, `description` (narrative)
  - `time_step` (integer position in the timeline)
  - `alternatives`: a list of possible actions at this node, each with a description, action type, and expected outcome summary.
  - `risks`: a non‑empty array of risk objects.
  - `source_citations`: list of cache IDs or URLs backing the node’s claims.
  - `confidence_score` (0.0–1.0)
  - `speculative` boolean flag.
- **Mandatory risk layer** — The system enforces:
  - Every node must have at least one `High` or `Critical` risk if it recommends a material change (investment, relocation, medical treatment, etc.).
  - Risk objects contain `severity`, `likelihood`, `description`, `mitigation_strategy`, and an optional `citation` linking to supporting evidence.
  - A Pydantic‑like validator (runtime schema checker) rejects any node that violates these constraints, triggering a targeted adversarial retry.
- **Citation anchoring & hallucination control**:
  - For any claim that relies on external information, the reasoner must embed an inline token `[Source: cache:<id> | <url>]` adjacent to the relevant sentence.
  - If a claim cannot be matched to a knowledge chunk with similarity ≥0.8, the reasoner must set `speculative: true` and tag it with `[Source: speculative]`.
  - A post‑generation citation audit scans the output and automatically fails nodes with missing or invalid citations, forcing a re‑prompt.
- **Adversarial retry loop** — On validation failure (missing risks, insufficient citations, malformed JSON), the system constructs a minimal, direct re‑prompt that tells the LLM exactly what was wrong and how to fix it. Retries are capped (default 3) with exponential backoff. If all retries fail, the node is flagged as `generation_failed` and the user is notified.
- **Confidence scoring methodology** — The `confidence_score` is a composite of:
  - Maximum/average semantic similarity of supporting chunks.
  - Source trust scores.
  - Cross‑persona agreement level (standard deviation among persona scores).
  - Presence and quality of citations.
  - The formula is calibrated so that low‑evidence nodes never score above 0.5.

## 6. Simulation & Decision Graph Engine

- **Immutable upstream snapshots** — Once a user chooses an alternative and creates a child node, the entire path from root to the parent is locked. Any further branching from that parent will never modify the locked ancestors, guaranteeing reproducibility and auditability.
- **Incremental simulation** — Branch creation requests carry only:
  - `parent_summary`: a compressed representation of the parent node and its immediate context.
  - `delta_context`: new evidence or user actions since the parent was created.
  - `knowledge_nuggets`: the top‑K relevant chunks for the specific branch decision.
  - The engine never re‑ingests or re‑computes the entire history, drastically reducing token usage and latency.
- **Automated world‑building** — On initial simulation start, the engine can generate a configurable number of future time steps (default 3), producing a baseline decision tree that the user can immediately explore. This gives the user a “quick start” before they begin manual branching.
- **User‑driven branching** — The UI exposes every alternative listed in a node as an actionable button. Clicking it triggers a branch creation request, the engine generates the next node, and the graph visually extends in real time.
- **Game‑over / terminal state detection** — Domain‑specific rules (e.g., “runway months ≤ 0”, “net worth ≥ target”) can mark a node as terminal with a reason. Users can also manually mark paths as “resolved” or “abandoned”.
- **Divergent parallel timelines** — The graph supports multiple independent branches that do not interfere. Users can explore “what if I invest” and “what if I save cash” simultaneously, each maintaining its own sequence of nodes.
- **Time‑step ordering** — Every node carries a `time_step` integer. The graph layout is temporal, with the root at `t=0` and subsequent nodes arranged by month (3, 6, 12 months horizons). Users can filter the view to show only nodes within a specific time window.
- **Parameterised what‑if simulation** — Users can open a “what‑if panel” on any node, adjust numeric assumptions (e.g., salary, inflation rate, market return, tax bracket), and request a re‑simulation of the downstream sub‑graph. The engine re‑generates only the affected nodes using the new parameters, preserving the rest of the graph.

## 7. Personalization & Memory

- **Multi‑faceted user profile**:
  - **Static traits**: expertise level in relevant domains, risk tolerance (explicitly stated), personal values (e.g., “prioritise work‑life balance”), communication style preference, and current life situation (age, location, family status, income, savings, debt).
  - **Dynamic learned traits**: derived from the user’s decisions, ignored risks, branching choices, and explicit feedback (thumbs up/down on nodes, corrections via chat). These traits are updated after every session.
- **Three‑tier personalization depth**:
  - **Level 1 (Explorer)**: A simple profile template is filled once and used as a mild bias. No persistent memory across sessions beyond basic preferences.
  - **Level 2 (Enthusiast)**: The profile is enriched by every completed session. The system remembers past decision graphs, user‑selected paths, and domain‑specific adaptations. Retrieval of historical memories is triggered by similarity to the current query.
  - **Level 3 (Cognitive Twin)**: A continuously updated, comprehensive model of the user. It captures not only what they decided but how they reasoned, their typical blind spots, and their emotional reactions. The twin can even predict what the user *would* likely decide in a novel situation, helping to highlight potential cognitive biases.
- **Memory architecture**:
  - **Episodic memory**: A chronologically organised, compressed log of past sessions, key decisions, and outcomes (if reported).
  - **Semantic profile**: A set of embeddings and key‑value pairs representing the user’s domain knowledge, values, and priorities.
  - **Procedural memory**: The user’s preferred decision frameworks (e.g., weighted criteria, minimax, regret minimisation) — either explicitly selected or inferred.
  - **Retrieval**: At inference time, a context‑aware memory retriever fetches the most relevant episodes and profile facets, using a combination of vector similarity and graph traversal (e.g., “find past decisions where the user faced a similar trade‑off”).
- **Graceful forgetting & compression** — To prevent memory bloat, old episodic data is progressively compressed into high‑level summaries (e.g., “In 2025, the user chose to prioritise salary over equity in three job decisions”). These summaries are themselves embeddable and searchable, ensuring long‑term retention without unbounded storage growth.

## 8. Context‑Aware Chatbot (Oracle Coach)

- **Node‑contextualised conversational interface** — Users can click on any node (or multi‑select nodes) and open a chat panel. The chatbot immediately understands the context of those nodes, their upstream paths, and the overall decision graph.
- **Full omnichannel context** — The chatbot’s context window is assembled from:
  - The full JSON of the selected node(s).
  - Compressed summaries of the upstream node chain.
  - The original user intent and clarifying Q&A.
  - The user’s profile and relevant memory snippets.
  - The underlying knowledge chunks and their source citations.
  - The last N messages of the current chat session (and optionally, past sessions about the same graph).
- **Advisory excellence**:
  - Translate complex decision logic into plain, actionable language.
  - Drill down into specific risks, explaining their likelihood and real‑world impact.
  - Generate step‑by‑step action plans, with precise, calculable next steps (e.g., “Allocate ₹60,000 to a Nifty 50 index fund via Zerodha”).
  - Perform on‑the‑fly calculations using node data and external formulas (compound interest, tax projections, currency conversion) via a **structured tool call** to a safe arithmetic engine.
  - Compare two parallel branches quantitatively and qualitatively, producing a side‑by‑side table with pros/cons and risk assessments.
  - Answer follow‑ups with full awareness of the entire decision landscape, not just the selected nodes.
- **Graph‑editing agent (Construction Mode)**:
  - Users can give natural language commands such as “What if I also consider freelancing on the side?” or “Simulate the next 9 months if I take the Berlin job.”
  - The chatbot translates the intent into a structured `GraphAction` (e.g., `create_branch`, `add_node`, `modify_parameter`), which is sent to the Simulation Engine for validation and execution.
  - The graph updates in real‑time; the new node appears with full citations and risks, and the chatbot announces the change and provides a summary.
  - This effectively makes the chatbot an alternative, conversational UI for building and extending the decision graph.
- **Permission gating & safety** — Graph modifications can be configured to always require user confirmation before committing. Read‑only actions (explanations, calculations) never require confirmation.
- **Rich citation display** — Chatbot responses mirror the node citation system: claims are annotated with clickable source links. References to specific nodes appear as interactive chips that, when clicked, scroll to that node and highlight it in the graph.

## 9. Accuracy, Hallucination Mitigation & Trust

- **Multi‑source triangulation** — A fact is elevated to `verified` only if it is corroborated by at least N independent, high‑trust sources (N configurable per domain, typically 2–3). This reduces reliance on any single potentially erroneous page.
- **Contradiction detection & surfacing** — The system actively identifies when sources disagree on a key claim. Instead of silently picking one, it presents the controversy to the user with a “disputed” badge and shows the conflicting evidence from both sides.
- **Confidence calibration** — The `confidence_score` is not merely a retrieval metric; it is penalised when:
  - Source trust is low.
  - Personas disagree strongly.
  - Citations are sparse or low‑quality.
  - The claim is about a highly volatile domain (e.g., cryptocurrency).
  - The score is clearly communicated: 0.9+ “High confidence”, 0.7–0.9 “Moderate”, below 0.5 “Speculative — treat with caution”.
- **Speculative marking (visual language)** — Any node or chat response that contains `speculative: true` claims is rendered with a distinct amber/orange border, a warning icon, and a tooltip explaining that the information is unverified. Users learn to immediately distinguish grounded insights from educated guesses.
- **Automated citation audit** — A post‑generation pipeline scans the entire node text, using regex and a small NLI model to verify that every assertive statement has a corresponding citation token. Missing citations cause the node to be rejected and re‑prompted.
- **Closed‑loop feedback & improvement**:
  - Users can rate nodes and chatbot responses (thumbs up/down) and provide textual corrections.
  - This feedback is fed into a continuous evaluation dataset, used to fine‑tune prompts, adjust source trust scores, and detect systematic errors (e.g., a particular persona consistently ignores tax implications).
  - Over time, the system’s error rate in high‑stakes domains (finance, health) can be measured and reduced, forming the backbone of a research paper.
- **Adversarial stress‑testing by design** — Because multiple personas naturally challenge each other, blind spots that a single‑answer system would miss are surfaced regularly. This built‑in red‑teaming is a key defence against over‑optimistic or dangerous recommendations.

## 11. Non‑Functional Requirements (Expanded)

- **Ultra‑high factual accuracy** — The system must achieve a hallucination rate (factual errors per decision node) below 5% for grounded claims, measured against a held‑out evaluation set of domain‑expert annotated scenarios.
- **Extreme personalization** — After 10+ sessions, the system should correctly predict the user’s preferred decision in a known scenario at least 70% of the time, and adapt its advice accordingly.
- **Lifelong memory with sub‑second retrieval** — Even with years of compressed episodic data, fetching relevant past memories must complete in under 200ms (local) or 500ms (cloud). Compression algorithms must maintain retrieval relevance above 90% compared to full memory storage.
- **Level 3 performance on minimal hardware** — The desktop application must launch within 30 seconds on a machine with Intel i5‑12400, 8 GB DDR4 RAM, integrated graphics, and a 256 GB SSD. Under typical usage (1 graph generation + 5 chat interactions per hour), total system memory footprint must stay under 6 GB, with CPU utilisation below 60%.
- **Absolute privacy by default (Level 3)** — The local application must never initiate outbound network connections except for explicitly user‑approved actions (e.g., cloud sync, manual scrape). All data at rest is encrypted (AES‑256), and the user holds the encryption keys.
- **Cloud scalability & cost efficiency** — The cloud tier should support 1,000 concurrent users on a budget of <$500/month for compute, using serverless functions where possible and queue‑based background processing for scraping.
- **Observability & transparency** — The system must emit structured logs (JSON) containing: latency per pipeline stage, cache hit rate, similarity scores, number of retries, confidence breakdown, and source trust levels. On desktop, a local dashboard shows these metrics to the power user. Cloud deployment integrates with standard monitoring (Sentry, Langfuse).

## 14. Evaluation & Research Readiness (Enhanced)

- **Reproducible benchmark construction** — The platform includes tools to create a “decision scenario benchmark”: a set of initial prompts, ground‑truth optimal paths (annotated by domain experts), and expected risks. This benchmark can be versioned and shared for academic comparisons.
- **Multi‑dimensional evaluation metrics**:
  - **Factual accuracy**: % of node claims that are fully supported by provided citations (manually verified on a test set).
  - **Risk recall**: % of known, expert‑identified risks that appear in the generated node.
  - **Source fidelity**: % of citations that point to the exact chunk supporting the claim (no hallucinated citations).
  - **User‑rated confidence alignment**: correlation between system confidence score and user‑perceived trustworthiness.
  - **Decision quality improvement**: a longitudinal metric measured by having users make decisions with vs. without the tool and comparing outcomes (e.g., financial return, job satisfaction) after 3‑6 months.
- **Comparison baselines** — The system is evaluated against:
  - ChatGPT‑4 / Claude 3.5 with simple prompt (“Give me a decision tree with risks…”).
  - Perplexity / Elicit (source‑cited Q&A but without branching simulation).
  - Vanilla RAG pipeline (chunk retrieval + single‑shot LLM with no adversarial or graph layer).
- **Reproducibility support** — For paper submissions, the system can export a snapshot of the entire knowledge base, the code version (Docker image or Git hash), and the exact prompt templates used, ensuring any researcher can rerun the experiments.
- **Continuous regression testing** — An automated test suite runs nightly, feeding a fixed set of queries and comparing output against known‑good references. Drift in accuracy, risk coverage, or citation quality triggers an alert, preventing silent degradation as the knowledge base evolves.

│ │ • Split at natural paragraph boundaries (~400-700 chars)      │ │
│ │ • Preserve headings, lists, tables as atomic units            │ │
│ │ • NO summarization at chunking stage — keep original text     │ │
│ │ • Parent-child chunking: small for retrieval, large for LLM  │ │
│ └──────────────────────────────────────────────────────────────┘ │
│                              │                                    │
│                              ▼                                    │
│ ┌──────────────────────────────────────────────────────────────┐ │
│ │ 2e. EMBEDDING + ENTITY EXTRACTION                             │ │
│ │ • Embed each chunk with BGE-M3 / Jina embeddings v3           │ │
│ │ • Extract entities (spaCy NER + SLM for complex entities)    │ │
│ │ • Extract relationships: causes, supports, refutes, etc.     │ │
│ │ • Build Knowledge Graph triples (Subject-Predicate-Object)   │ │
│ └──────────────────────────────────────────────────────────────┘ │
│                              │                                    │
│                              ▼                                    │
│ ┌──────────────────────────────────────────────────────────────┐ │
│ │ 2f. MULTI-INDEX STORAGE                                       │ │
│ │ • Vector Index: pgvector (Cloud) / LanceDB (Local)            │ │
│ │ • BM25 Index: Postgres FTS (Cloud) / SQLite FTS5 (Local)     │ │
│ │ • Knowledge Graph: Neo4j (Cloud) / SQLite+Adjacency (Local)  │ │
│ │ • Document Store: S3/MinIO (Cloud) / Local filesystem        │ │
│ │ • All with TTL, provenance, verification_status              │ │
│ └──────────────────────────────────────────────────────────────┘ │
└────────────────────────────────────┬────────────────────────────┘
                                     │
                                     ▼
┌─────────────────────────────────────────────────────────────────┐
│ STEP 3: HYBRID RETRIEVAL + GRAPH TRAVERSAL                       │
│                                                                  │
│ ┌──────────────────────────────────────────────────────────────┐ │
│ │ 3a. PARALLEL RETRIEVAL                                        │ │
│ │ • Dense: Vector similarity search (cosine, top-K=20)          │ │
│ │ • Sparse: BM25 keyword search (top-K=20)                      │ │
│ │ • Graph: Entity-linked multi-hop traversal                    │ │
│ │   Example: "a" → related_to → "2" → supported_by → "b"       │ │
│ │ • SQL: For exact numeric data / user profile lookups          │ │
│ └──────────────────────────────────────────────────────────────┘ │
│                              │                                    │
│                              ▼                                    │
│ ┌──────────────────────────────────────────────────────────────┐ │
│ │ 3b. RRF FUSION + CROSS-ENCODER RERANK                         │ │
│ │ • Reciprocal Rank Fusion merges all retrieval sources         │ │
│ │ • Cross-encoder reranker (Qwen3-Reranker-8B / Cohere v3)     │ │
│ │   scores each (query, chunk) pair individually                │ │
│ │ • Output: Ranked top-K evidence chunks (K=5-10)               │ │
│ └──────────────────────────────────────────────────────────────┘ │
│                              │                                    │
│                              ▼                                    │
│ ┌──────────────────────────────────────────────────────────────┐ │
│ │ 3c. GRAPH EXPANSION + CONFLICT DETECTION                      │ │
│ │ • Expand evidence subgraph: pull neighbor entities/relations │ │
│ │ • Detect contradictions: flag when sources disagree           │ │
│ │ • Freshness ranking: boost recent content, penalize expired   │ │
│ └──────────────────────────────────────────────────────────────┘ │
│                              │                                    │
│                              ▼                                    │
│ ┌──────────────────────────────────────────────────────────────┐ │
│ │ 3d. CONTEXT COMPRESSION + CITATION MAPPING                    │ │
│ │ • Compress evidence using LLMLingua-2 to fit token budget     │ │
│ │ • Map every factual claim to exact source chunk (citation)    │ │
│ │ • Build citation_token → chunk_id lookup table                │ │
│ └──────────────────────────────────────────────────────────────┘ │
└────────────────────────────────────┬────────────────────────────┘
                                     │
                                     ▼
┌─────────────────────────────────────────────────────────────────┐
│ STEP 4: MULTI-PERSONA ADVERSARIAL REASONING                      │
│                                                                  │
│ ┌──────────────────────────────────────────────────────────────┐ │
│ │ 4a. CONTEXT ASSEMBLY (per node, per time_step)                │ │
│ │ • Parent summary (compressed upstream path)                   │ │
│ │ • Top-K evidence chunks with citations                        │ │
│ │ • User profile (Level 1/2/3 depth varies)                     │ │
│ │ • Relevant episodic memories (past similar decisions)         │ │
│ │ • Persona prompt template                                     │ │
│ └──────────────────────────────────────────────────────────────┘ │
│                              │                                    │
│                              ▼                                    │
│ ┌──────────────────────────────────────────────────────────────┐ │
│ │ 4b. PARALLEL PERSONA EXECUTION (3-5 instances)                │ │
│ │ • Each persona runs with different temperature (0.5-0.8)     │ │
│ │ • Strict JSON Schema enforcement: DecisionNode format         │ │
│ │ • Temperature + seed for reproducibility when needed          │ │
│ │ • Personas: Skeptical Investor, Cautious Regulator,           │ │
│ │   Aggressive Founder, Ethical Auditor, Optimist                │ │
│ └──────────────────────────────────────────────────────────────┘ │
│                              │                                    │
│                              ▼                                    │
│ ┌──────────────────────────────────────────────────────────────┐ │
│ │ 4c. SYNTHESIS ARBITER                                         │ │
│ │ • Compare all persona nodes                                   │ │
│ │ • Identify: consensus areas, contradictions, unique risks     │ │
│ │ • Produce final balanced DecisionNode                         │ │
│ │ • Include minority dissenting views in metadata               │ │
│ │ • Compute confidence_score from agreement + evidence quality  │ │
│ └──────────────────────────────────────────────────────────────┘ │
└────────────────────────────────────┬────────────────────────────┘
                                     │
                                     ▼
┌─────────────────────────────────────────────────────────────────┐
│ STEP 5: VALIDATION + GUARDRAILS                                  │
│                                                                  │
│ ┌──────────────────────────────────────────────────────────────┐ │
│ │ • Grounding Check: NLI model verifies claims vs chunks        │ │
│ │ • Citation Audit: Every assertive claim has [Source: ...]     │ │
│ │ • Risk Enforcement: ≥1 High risk if material action proposed  │ │
│ │ • Schema Validation: Pydantic v2 strict mode                  │ │
│ │ • Speculative Flagging: Claims without evidence marked        │ │
│ │ • Confidence Calibration: Cap score if evidence is weak       │ │
│ └──────────────────────────────────────────────────────────────┘ │
│                              │                                    │
│                     ┌───────┴───────┐                            │
│                     │ PASS / FAIL   │                            │
│                     └───────┬───────┘                            │
│                             │                                     │
│              ┌──────────────┴──────────────┐                     │
│              ▼                             ▼                     │
│         ┌─────────┐                 ┌───────────┐                │
│         │  PASS   │                 │   FAIL    │                │
│         │ Persist │                 │ Targeted  │                │
│         │  Node   │                 │ Retry (3x)│                │
│         └─────────┘                 │ + Backoff │                │
│                                     └───────────┘                │
└────────────────────────────────────┬────────────────────────────┘
                                     │
                                     ▼
┌─────────────────────────────────────────────────────────────────┐
│ STEP 6: GRAPH PERSISTENCE + UI UPDATE                             │
│                                                                  │
│ • Lock upstream nodes (immutable snapshots)                      │
│ • Create edge from parent → new node                             │
│ • Update session metadata                                        │
│ • Push to frontend via WebSocket (React Flow update)             │
│ • Trigger evaluation sampling (store for RAGAS later)            │
│ • Log trace to Langfuse for observability                        │
└─────────────────────────────────────────────────────────────────┘
```

## Memory Architecture: The User Twin

Based on 2026 research (AdaMem, RGMem, MemMachine), this is the complete memory fabric:

```
┌─────────────────────────────────────────────────────────────────┐
│                      MEMORY FABRIC (5 LAYERS)                     │
│                                                                  │
│  ┌────────────────────────────────────────────────────────────┐ │
│  │ LAYER 1: WORKING MEMORY (Short-Term)                       │ │
│  │ • Current session context (active nodes, recent chat)       │ │
│  │ • Redis (Cloud) / In-Memory dict (Local)                   │ │
│  │ • TTL: Session duration, max 24 hours                      │ │
│  │ • <10ms retrieval for active context                        │ │
│  └────────────────────────────────────────────────────────────┘ │
│                              │                                    │
│                              ▼                                    │
│  ┌────────────────────────────────────────────────────────────┐ │
│  │ LAYER 2: EPISODIC MEMORY (Decision History)                │ │
│  │ • Every completed decision graph (compressed)              │ │
│  │ • Key decisions, paths chosen, feedback given              │ │
│  │ • Post-session compression: full graph → summary +          │ │
│  │   key nodes (using SLM summarization)                       │ │
│  │ • Vector indexed for semantic search                        │ │
│  │ • "Find past decisions where I faced a similar trade-off"  │ │
│  └────────────────────────────────────────────────────────────┘ │
│                              │                                    │
│                              ▼                                    │
│  ┌────────────────────────────────────────────────────────────┐ │
│  │ LAYER 3: SEMANTIC/PERSONA MEMORY (User Profile)            │ │
│  │ • Static traits: expertise, risk_tolerance, values,         │ │
│  │   communication_style, life_situation                      │ │
│  │ • Dynamic traits: inferred preferences, decision patterns, │ │
│  │   common biases, emotional reactions                        │ │
│  │ • Updated after every session via RGMem-style               │ │
│  │   hierarchical coarse-graining                              │ │
│  │ • Stored as structured JSON + embedding vector              │ │
│  └────────────────────────────────────────────────────────────┘ │
│                              │                                    │
│                              ▼                                    │
│  ┌────────────────────────────────────────────────────────────┐ │
│  │ LAYER 4: PROCEDURAL MEMORY (Decision Frameworks)            │ │
│  │ • Preferred decision methods (weighted criteria, minimax)   │ │
│  │ • Learned from observing user's branching patterns          │ │

│  │   deciding, and always checks tax implications"             │ │

│                              │                                    │
│                              ▼                                    │
│  ┌────────────────────────────────────────────────────────────┐ │
│  │ LAYER 5: RELATIONAL/GRAPH MEMORY (Knowledge Connections)    │ │
│  │ • Entity-relationship graph built from all interactions    │ │
│  │ • User's personal connections between concepts              │ │
│  │ • "This user connects 'startup' with 'Berlin' and           │ │
│  │   'remote work' — they're exploring tech migration"         │ │
│  │ • Graph traversal enables multi-hop memory recall           │ │
│  └────────────────────────────────────────────────────────────┘ │
│                                                                  │
│  ┌────────────────────────────────────────────────────────────┐ │
│  │ MEMORY EVOLUTION LOOP (Continuous Learning)                │ │
│  │                                                            │ │
│  │ New Interaction ──→ Working Memory ──→ Session End         │ │
│  │                                            │                │ │
│  │                              ┌─────────────┘                │ │
│  │                              ▼                              │ │
│  │                    Episodic Compression                     │ │
│  │                    (SLM summarizes full graph)              │ │
│  │                              │                              │ │
│  │                    ┌─────────┴──────────┐                   │ │
│  │                    ▼                    ▼                   │ │
│  │           Semantic Profile        Relational Graph          │ │
│  │           Update (RGMem-style     Update (new entities      │ │
│  │           hierarchical            + relationships           │ │
│  │           coarse-graining)        added to graph)           │ │
│  │                    │                    │                   │ │
│  │                    └────────┬───────────┘                   │ │
│  │                             ▼                               │ │
│  │                  Procedural Pattern Update                  │ │

│  │                   observed consistently)                    │ │
│  └────────────────────────────────────────────────────────────┘ │
│                                                                  │
│  INTEGRATION: Mem0 (mem0ai) for adaptive memory management       │

## Query-Time Pipeline (End-to-End Flow)
```
USER QUERY ARRIVES
    │
    ▼
[Auth + Tenant Context] ──→ Who is this? What level? What permissions?
    │
    ▼
[Intent Classification] ──→ Fast SLM: What does user want?
    │                        (new_graph / branch / chat / what-if / research)
    │
    ▼
[Safety Classification] ──→ PII check, harm detection, compliance
    │
    ▼
[Route Selection] ──→ Which pipeline? Decision Graph / Branch / Chat / Research
    │
    ▼
[Query Transformation] ──→ Rewrite, entity-link, decompose, apply filters
    │
    ▼
[Retrieval Fabric] ──→ Dense + Sparse + Graph + SQL + Web (parallel)
    │
    ▼
[Fusion + Rerank] ──→ RRF merge → Cross-encoder → Top-K
    │
    ▼
[Context Compression] ──→ Fit token budget, preserve citations
    │
    ▼
[Memory Injection] ──→ Pull relevant episodic + profile + procedural memories
    │
    ▼
[Prompt Assembly] ──→ System prompt + evidence + persona + memory + schema
    │
    ▼
[LLM / Agent Execution] ──→ Single call or agentic loop with tool calls
    │
    ▼
[Validation] ──→ Grounding, citation audit, schema, risk, policy check
    │
    ▼
[Retry if Failed] ──→ Targeted re-prompt (max 3x)
    │
    ▼
[Response Assembly] ──→ Graph JSON + citations + chat + share URL
    │
    ▼
[Logging + Feedback + Memory Update] ──→ Langfuse trace + user feedback loop
```
## Key Design Principles (Simplified)
1. **Route, don't guess.** The Intent Classifier determines which of the 5 pipelines to use before any heavy computation begins.
2. **Hybrid retrieval always beats pure vector.** Combining dense vectors, BM25, and graph traversal — then fusing with RRF and reranking with a cross-encoder — consistently outperforms single-method approaches by 15-30%.
3. **Small models for routing, big models for reasoning.** SLMs (1-4B params) handle classification, extraction, and rewrite tasks at sub-second latency with zero marginal cost. Reserve large reasoning models for node generation and chat.
4. **Memory is a fabric, not a database.** Five interconnected layers (working, episodic, semantic/persona, procedural, relational) create a living user twin that evolves with every interaction.
5. **Adversarial reasoning reduces over-optimism.** Running 3-5 personas in parallel and synthesizing their outputs surfaces blind spots that single-model approaches miss.
6. **Validate before persisting.** Every node must pass grounding checks, citation audits, risk enforcement, and schema validation. Failures trigger targeted retries, not silent errors.
7. **Tools are standardized via MCP.** All external capabilities (search, calculate, create_branch) are exposed through the Model Context Protocol, making the system extensible without code changes.
8. **Observe everything.** Langfuse traces every retrieval, every LLM call, every tool execution. RAGAS runs nightly to detect quality drift before users notice.
This pipeline is complete, clear, and feasible. It maps directly to your Decision Graph Simulator vision while incorporating every major 2026 advancement: hybrid retrieval with reranking, GraphRAG with knowledge graph traversal, multi-persona adversarial synthesis, MCP-standardized tool calling, five-layer adaptive memory, and continuous evaluation with Langfuse + RAGAS. Every component is specified, every decision justified, and the entire system can be built incrementally — starting with the stateless oracle and growing into the full cognitive platform.

## 1. Introduction

This document is the **single source of truth** for every REST endpoint exposed by the Decision Graph Simulator (DGS) platform. It covers the full journey from raw user prompt to interactive decision graph, personalised chatbot, and platform features. Endpoints are labelled with the version in which they first appear (v0.1 → v1.0).

### 1.1 Authentication

| Version | Method |
|---------|--------|
| v0.1 | No authentication (stateless, ephemeral sessions) |
| v0.2+ | **Bearer token** (JWT) issued by Supabase Auth. Include in header: `Authorization: Bearer <token>` |

All endpoints marked **Auth: Required** demand a valid user token. Public endpoints (e.g., shared graphs) require no authentication.

### 1.2 API Versioning

The API uses **URL versioning**. The current version is `v1`.  
Example: `POST /v1/simulate/start`

### 1.3 Response Envelope

Every response follows a consistent envelope:

```json
{
  "data": { ... },
  "meta": { "request_id": "uuid", "timestamp": "ISO8601" }
}
```

Errors are returned with an `error` object:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Human-readable description",
    "details": []
  }
}
```

### 1.4 Common HTTP Status Codes

| Code | Meaning |
|------|---------|
| 200 | Success |
| 201 | Resource created |
| 202 | Accepted (async job started) |
| 204 | No content (successful deletion) |
| 400 | Bad request (validation failure) |
| 401 | Unauthorized (missing/invalid token) |
| 402 | Payment required (quota exceeded) |
| 404 | Resource not found |
| 409 | Conflict (e.g., duplicate resource) |
| 429 | Too many requests (rate limited) |
| 500 | Internal server error |

This is the complete, versioned, and final API contract for the Decision Graph Simulator platform. It supports every feature from the stateless v0.1 oracle to the fully personalised, locally‑running cognitive twin.
